# PostgreSQL foundation — Sprint 15A

## Audited starting point and architecture

The backend already declared SQLAlchemy 2.0, psycopg 3 and Alembic, but its
declarative metadata and migration directory were empty. Its original Alembic
template emitted `pass` even for autogenerated changes; that template is now
fixed. The previous engine/session module was not called by any route. The
collector replaces `story_service._latest_stories`; editorial demo drafts live
in `editorial_story_service._editorial_story_overrides`. Both remain unchanged.

This sprint adds a separate persistence layer, not a storage switch. PostgreSQL
16 runs in a dedicated container and named volume exclusively for Hype News Hub.
The `database` Docker bridge is internal; only this application's backend and
migration tool join it. PostgreSQL has no published host port. The frontend
remains on the existing application network. No cloud database or other Hype
product is involved.

The existing backend Dockerfile and frontend/Render/Vercel configuration are
unchanged. `backend/Dockerfile.database` packages schema tools and migrations
for local/self-hosted use only. Migrations are an explicit operator action and
are never run automatically by API startup.

```text
frontend ── application network ── FastAPI (existing in-memory routes)
                                      │ private database network
schema tools ─────────────────────────┤
                                      └─ postgres:16-alpine → postgres-data volume

database-tests ── separate private test network ── postgres-test (disposable tmpfs)
```

## Schema and identity rules

| Table | Purpose and integrity rules |
| --- | --- |
| `news_sources` | UUID identity, unique source URL, original name, connector, language and enabled flag. Disable sources rather than deleting referenced provenance. |
| `collected_articles` | UUID identity; source FK; original external ID and URL; optional canonical URL; original title, excerpt, body, media URL, language, categories and raw JSONB; optional SHA-256 content hash and first-seen run FK. |
| `stories` | UUID identity, headline, existing story status vocabulary, bounded similarity, date, language and categories. |
| `story_articles` | Composite `(story_id, article_id)` primary key, one current story per article, optional match score, and a partial unique index allowing at most one primary article per story. |
| `collection_runs` | UUID identity, start/finish times, running/completed/partial/failed status, request limit, source/article/story counts and optional error. |
| `collection_source_results` | UUID identity, unique `(run_id, source_id)`, per-source status, counts, timestamps and error. |

Article uniqueness is scoped to its source: `(source_id, external_id)`,
`(source_id, url)` and `(source_id, canonical_url)`. Two sources may retain the
same external ID or URL independently. Unknown IDs/canonical URLs are SQL NULL,
not empty strings. Original URLs and source identifiers are retained unchanged;
Sprint 15B must normalize canonical identity before inserting/upserting. These
constraints support idempotency but do not implement collection upserts yet.
UUIDs remain stable once stored; callers resolve repeated intake to those rows.

Foreign keys reject dangling source/article references. Deleting a story deletes
its memberships, not its source articles. Deleting a collection run deletes its
source-result rows and clears optional article first-seen references. Deleting
referenced sources/articles is restricted. A primary membership is selected
transactionally by the future collector; the schema permits an initially empty
story and enforces at most one primary, not exactly one.

Dates use PostgreSQL `timestamptz`; Python callers should supply aware datetimes.
Article raw payloads use JSONB and categories use `text[]`. UUID and timestamp
server defaults also support SQL inserts outside the ORM. `updated_at` is
updated by SQLAlchemy writes; direct SQL/upserts must set it explicitly. Aggregate
run counts are stored snapshots, not automatically maintained database totals.
No editorial drafts, approvals, AI, publishing, or audit-event schema is added.

## Ubuntu setup

Install Docker Engine and its Compose plugin using the
[official Ubuntu instructions](https://docs.docker.com/engine/install/ubuntu/).
Check `docker version` and `docker compose version`. Use a Python
virtual environment for optional native backend development. Docker is sufficient
for migrations and database tests; no host PostgreSQL installation is required.

For an optional native Ubuntu backend environment on a fresh checkout:

```bash
sudo apt-get update
sudo apt-get install python3-venv python3-pip
python3 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.txt
cd backend
cp .env.example .env
.venv/bin/uvicorn app.main:app --reload
```

The native API still uses memory and can run with the blank database password
in this example. Return to the repository root for Compose commands below.

On a fresh checkout, from the repository root:

```bash
cp .env.example .env
chmod 600 .env
python3 - <<'PY'
from pathlib import Path
import secrets
path = Path('.env')
content = path.read_text()
for key in ('POSTGRES_PASSWORD', 'POSTGRES_TEST_PASSWORD'):
    content = content.replace(key + '=\n', key + '=' + secrets.token_hex(32) + '\n')
path.write_text(content)
PY
docker compose config --quiet
docker compose up -d --wait postgres
docker compose --profile tools run --rm --build migrate
docker compose up -d --build backend frontend
```

Do not overwrite an existing `.env` or regenerate an established database's
password this way. The root `.env` controls Compose interpolation;
`backend/.env` is only for a native backend process. Examples contain no usable
password. `.env` and local backups are ignored by Git. Database access requires
`POSTGRES_PASSWORD`; importing/starting the current memory-based API does not.

Compose uses `postgres` as the database hostname. PostgreSQL is not reachable
through `localhost:5432` by default. Prefer running database tools in the tools
container. Native Ubuntu development may continue to run the API/frontend
without DB access in Sprint 15A. For native tools on Darkić's private network,
set `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER` and
`POSTGRES_PASSWORD` in `backend/.env` to that dedicated private instance.

SQLAlchemy builds an escaped URL from separate environment fields, including
passwords with `@`, `:`, `/` or `%`; its normal representation redacts passwords.
Sessions use bounded pools and connection timeouts, pre-ping, parameter hiding,
and rollback/close handling. `session_scope()` owns a commit/rollback unit of
work. The unused `get_db()` dependency does not implicitly commit on success;
future services must own their transaction boundaries.

`POSTGRES_SSLMODE` defaults to `prefer` for the private local container. A
self-hosted installation with PostgreSQL TLS configured can use `verify-full`
and supply the trusted CA through libpq's `PGSSLROOTCERT`. Never open the database
to the public internet or reuse another product's instance. Docker's
`POSTGRES_USER` is a bootstrap/schema-owner account; provision a separate
non-superuser runtime role before wiring production ingestion in Sprint 15B.

Passwords in an initialized PostgreSQL volume are not changed by editing `.env`.
Rotate them using an authenticated database operation and update clients together.
The named volume belongs to the Compose project: keep the project name stable.
`docker compose down` preserves it. `docker compose down --volumes` destroys it.
Container health checks test database availability, not migration readiness;
the API's `/` endpoint remains its existing liveness check.

## Migrations

```bash
docker compose --profile tools run --rm migrate alembic current
docker compose --profile tools run --rm migrate alembic upgrade head
docker compose --profile tools run --rm migrate alembic check
docker compose --profile tools run --rm migrate alembic history
```

The initial revision is `20261030_01`. It is a frozen, reversible DDL migration;
it does not call the current models' `create_all()` or seed live data. The normal
`alembic.ini` contains no credentials. The migration environment imports all
models and supports injected connections for isolated integration tests.

For future revisions, create them from a native development environment connected
to the dedicated development database, using `cd backend` and
`alembic revision --autogenerate -m description`. Review generated DDL before
applying it; autogenerated migrations do not substitute for data-migration design.
Rebuild the tools image after changing models or migrations. Do not use
`alembic downgrade base` to recover a populated application database: it drops
these tables. Downgrade/re-upgrade verification below uses only the test instance.

## Tests

Existing regression/configuration tests need no running database:

```bash
cd backend
python -B -m unittest discover -s tests -v
```

PostgreSQL integration tests are explicitly opt-in and never use SQLite. From
the repository root, with both generated passwords in the root `.env`:

```bash
docker compose --profile test up -d --wait postgres-test
docker compose --profile test run --rm --build database-tests
docker compose --profile test stop postgres-test
docker compose --profile test rm -f postgres-test
```

The test instance uses tmpfs, a separate internal network, no published port and
no application volume. The runner sets `RUN_POSTGRES_TESTS=1`, uses
`hype_news_hub_test`, and refuses a different name or existing application tables.
It creates its schema using Alembic, checks model constraints and foreign keys,
verifies stable identity/data in new sessions, tests commit/rollback and source
attribution, and checks upgrade → metadata comparison → downgrade → re-upgrade.
Tests clean only the schema they created after confirming an empty test database.
If interrupted, recreate only the disposable `postgres-test` container.

Run frontend compatibility checks from `frontend/` with `npm test`,
`npm run typecheck` and `npm run build`. API routes and Pydantic response schemas
have not changed; collector, matcher, editorial services and frontend are unwired
from the new database layer.

## Backup and recovery

Create a logical custom-format backup from the private container (root directory):

```bash
umask 077
mkdir -p backups
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' > "backups/hype-news-hub-$(date -u +%Y%m%dT%H%M%SZ).dump"
```

Check the command's exit code and archive contents, schedule backups on Darkić's
host, and retain encrypted copies on storage independent of the Docker volume.
The named volume is persistence, not a backup. Do not copy a running data directory
as an uncoordinated filesystem backup. `pg_dump` does not include cluster roles;
retain the separate role/credential provisioning procedure securely.

Restore first into a **new database**, using a PostgreSQL client of the same
major version, rather than overwriting the active one:

```bash
docker compose exec -T postgres sh -c 'createdb -U "$POSTGRES_USER" hype_news_hub_restore'
docker compose exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d hype_news_hub_restore --exit-on-error --no-owner --no-privileges' < backups/CHOSEN_BACKUP.dump
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d hype_news_hub_restore -v ON_ERROR_STOP=1 -c "SELECT version_num FROM alembic_version;"'
docker compose --profile tools run --rm -e POSTGRES_DB=hype_news_hub_restore migrate alembic current
docker compose --profile tools run --rm -e POSTGRES_DB=hype_news_hub_restore migrate alembic check
```

Verify expected counts, source attribution and application version compatibility
before an approved database cutover. Apply newer migrations to the restored
copy if required. Keep the original database/backup until recovery is verified.
Volume loss requires restoring a backup; restarting a container cannot recover
deleted data. Test restores regularly instead of relying only on successful dumps.

## Remaining Sprint 15B work

Seed/upsert configured sources; map normalized articles to persistent identities;
normalize canonical URLs and optional identifiers; reconcile unique-key conflicts;
persist each collection run/result transactionally; reuse story UUIDs; decide
membership/primary selection and merge/split rules; and switch the existing API
read/write paths while preserving public IDs/contracts. Persisted run/article
membership beyond the first-seen link, retries/checkpoints, concurrency handling,
aggregate count updates, runtime-role grants, retention and operational monitoring
still need an explicit ingestion design. Existing demo editorial drafts remain
in memory. URL uniqueness uses exact PostgreSQL text values and B-tree indexes;
ingestion must define normalization and handling of exceptionally long URLs
before accepting arbitrary upstream data. PostgreSQL foundation alone does not
make current API state durable.

# PostgreSQL foundation and persistent collection — Sprints 15A/15B

## Audited starting point and architecture

The backend already declared SQLAlchemy 2.0, psycopg 3 and Alembic, but its
declarative metadata and migration directory were empty. Its original Alembic
template emitted `pass` even for autogenerated changes; that template is now
fixed. The previous engine/session module was not called by any route. The
collector originally replaced `story_service._latest_stories`. This remains the
default memory-mode behavior. Explicit PostgreSQL mode now uses the repository
for collection, story lists, editorial queues and source-article workspaces.
Editorial demo drafts still live in `editorial_story_service._editorial_story_overrides`
and remain non-durable placeholders, including in PostgreSQL mode.

`NEWS_STORAGE_BACKEND=memory|postgres` selects storage at process configuration;
there is no public storage-switch endpoint and no automatic fallback. PostgreSQL
16 runs in a dedicated container and named volume exclusively for Hype News Hub.
The `database` Docker bridge is internal; only this application's backend and
migration tool join it. PostgreSQL has no published host port. The frontend
remains on the existing application network. No cloud database or other Hype
product is involved.

The existing backend Dockerfile and frontend/Render/Vercel configuration are
unchanged. `backend/Dockerfile.database` packages schema tools and migrations
for local/self-hosted use only. Migrations are an explicit operator action and
are never run automatically by API startup.

```text
frontend ── application network ── FastAPI (memory default; opt-in PostgreSQL)
                                      │ private database network
schema tools ─────────────────────────┤
                                      └─ postgres:16-alpine → postgres-data volume

database-tests ── separate private test network ── postgres-test (disposable tmpfs)
```

## Schema and identity rules

| Table | Purpose and integrity rules |
| --- | --- |
| `news_sources` | UUID identity, unique source URL, original name, connector, language and enabled flag. Disable sources rather than deleting referenced provenance. |
| `collected_articles` | UUID identity; source FK; original external ID and URL; optional canonical URL; original title, excerpt, body, media URL, language, categories and raw JSONB; optional SHA-256 content hash and first-seen run FK. |
| `stories` | UUID identity, headline, existing story status vocabulary, bounded similarity, date, language and categories. |
| `story_articles` | Composite `(story_id, article_id)` primary key, one current story per article, optional match score, and a partial unique index allowing at most one primary article per story. |
| `collection_runs` | UUID identity, start/finish times, running/completed/partial/failed status, request limit, source/article/story counts and optional error. |
| `collection_source_results` | UUID identity, unique `(run_id, source_id)`, per-source status, counts, timestamps and error. |
| `article_identities` | Historical external IDs/URL aliases, bounded SHA-256 keys, source-scoped uniqueness and an FK enforcing article/source consistency. |

Article uniqueness is scoped to its source using generated 64-character SHA-256
keys for external IDs, original URLs and canonical URLs. Source URLs also use a
bounded key. Full text values are retained, without indexing unbounded text.
`hnh_identity_hash()` fixes UTF-8 conversion for deterministic database hashes.
Unknown optional identities are NULL, not empty strings. UUIDs are allocated only
for genuinely new records; historical aliases resolve updated URLs/IDs to the
same row. First-seen URLs/external IDs stay in article columns; latest observed
source metadata, including the original fetched URL and date string, is stored
separately for API serialization. Available WordPress body and original public
JSON payload are retained.

Canonicalization lowercases scheme/host, removes default ports, fragments,
known tracking parameters and WordPress trailing slash variants, and normalizes
unreserved percent escapes. HTTP/HTTPS, www/non-www, path case, meaningful query
values, duplicate parameters and their order remain distinct. Source identity
uses the same URL rules. No extra requests discover HTML canonical tags.
Changing a configured source's host creates a new source identity.

Identity rules are versioned in `app/core/url_identity_v1.py`; runtime intake
and migration `20261030_02` use that same implementation. Query components are
opaque URL bytes: `%FF`, `%FE`, `%EF%BF%BD`, `+`, `%20` and `%2B` stay distinct.
Only unreserved ASCII escapes are decoded; other escapes use uppercase hex.
Literal Unicode paths/queries become UTF-8 percent escapes, matching their
already-encoded equivalents without replacement characters. Malformed percent
escapes and embedded control characters fail the source batch
safely. Tracking keys are recognized after unreserved-ASCII normalization;
meaningful parameter order, duplicates, blank values and valueless parameters
are preserved. After this version is released, incompatible policy changes
require a new version and an explicit identity migration.

If identities point to different existing rows, the entire source batch fails
without choosing or deleting either row. A hash collision is also rejected.
Operators must investigate conflicting provenance; automatic destructive article
merges are excluded.

Foreign keys reject dangling source/article references. Deleting a story deletes
its memberships, not its source articles. Deleting a collection run deletes its
source-result rows and clears optional article first-seen references. Deleting
referenced sources/articles is restricted. A primary membership is selected
transactionally by the collector; the schema permits an initially empty
story and enforces at most one primary, not exactly one.

Dates use PostgreSQL `timestamptz`; Python callers should supply aware datetimes.
Article raw payloads use JSONB and categories use `text[]`. UUID and timestamp
server defaults also support SQL inserts outside the ORM. `updated_at` is
updated by SQLAlchemy writes; direct SQL/upserts must set it explicitly. Aggregate
run counts are stored snapshots, not automatically maintained database totals.
Existing article-to-story membership and primary articles are preserved. New
articles match existing primaries with the existing similarity function/threshold;
ties use story UUID order. New story UUIDs are generated only once. Current
member content refreshes headline/categories/scores; singleton similarity stays
zero. Existing stories are not automatically split/merged after headline edits.
No editorial drafts, approvals, AI, publishing, or general audit-event schema is added.

### Temporal eligibility for new memberships

In PostgreSQL mode, `STORY_MATCH_MAX_GAP_HOURS` defaults to `48` and must be
finite and positive. A new article can match a story only when its normalized
publication timestamp and the primary article's timestamp are both known,
timezone-aware and within that absolute gap, including the boundary. The
existing similarity threshold is applied only after this gate. Missing or
invalid dates create a separate singleton; collection time is never substituted.
Storage/display retains the existing UTC normalization policy. Matching is more
conservative: newly observed dates require an explicit timezone, or a matching
WordPress `date_gmt` raw field establishing UTC. Naive source-local fallback dates
cannot justify a new membership. Legacy typed `timestamptz` values without
observation metadata remain authoritative. Incorrect upstream dates/timezones
can still mislead matching; this gate does not verify the source's factual claims.

The primary article anchors the window, so coverage cannot extend a story
indefinitely through a chain of recent members. Repeated article identities
retain their existing story, even if dates/titles change or the window is
tightened. Existing memberships are not split, and this change does not repair
previously incorrect groupings. Recurring headlines months/years apart create
separate stories. Multi-day coverage beyond the configured window may need
future manual grouping. Memory-mode matching remains unchanged.

## Collection transactions and API behavior

A session-level PostgreSQL advisory lock serializes collection across API
processes. Concurrent collection returns HTTP 409 with `Retry-After: 10`.
The worker holds one pool connection, but no database transaction stays open
during source requests. Work runs in a worker thread so synchronous SQLAlchemy
does not block the API event loop.
Story reads use a read-only repeatable-read transaction so concurrent intake
cannot mix story metadata with memberships from a different committed snapshot.

The run/pending source results commit first. Each source's articles, aliases,
story memberships, counts and success result commit together. Source fetch,
normalization, identity and data failures mark that source failed after rollback;
other sources and previous collections remain intact. Database availability or
permission errors return HTTP 503, without switching to memory. When possible,
the run is finalized with an error. After a crash, the next exclusive collection
marks unfinished sources interrupted before starting a new run. A manual retry
reuses committed identities without duplicate articles or stories.
An interrupted finalization is `partial` when some source work committed, even
if every source succeeded; `collection_runs.error` records the pipeline failure.

Existing routes and JSON shapes are unchanged. In PostgreSQL mode, collection
`stories`/`stories_total` represent the complete retained story snapshot from
the finalization transaction, including successful empty and partial runs.
This matches the frontend's existing replacement behavior and `/api/stories`;
no second frontend refresh or storage-mode detection is required. Memory/demo
mode keeps its existing latest-run snapshot behavior.
UI counters label this total as available stories, not newly created records.

Collection `articles`/`articles_total` describe accepted unique observations
in that run, not just inserts; `story_candidates_total` remains a run metric.
Database run `stories_total` counts touched stories and can be zero while the
API snapshot contains retained stories. Run counts are snapshots, not live
archive totals or immutable article revisions. Story/queue/workspace reads
include all retained stories, so empty/failed intake does not erase persisted data.

Additive response headers are exposed through CORS:

| Header | Meaning |
| --- | --- |
| `X-News-Storage` | `memory` or `postgres` |
| `X-Collection-State` | `never_collected`, `running`, `completed`, `partial`, `failed`; HTTP 503 uses `unavailable` |
| `X-Collection-Run-Id` | Last/returned persisted run UUID, when present |
| `X-Collection-New-Articles` | New inserts in that run; unchanged intake returns `0` even if `articles_total` is positive |

Upstream failures retain HTTP 200 and existing failure counts/`source_results`.
A successful empty run has state `completed`, unlike `never_collected`. Existing
frontend screens remain compatible but do not yet display the additional headers.
Discovery remains a read-only connectivity probe.

## Ubuntu setup

Install Docker Engine and its Compose plugin using the
[official Ubuntu instructions](https://docs.docker.com/engine/install/ubuntu/).
Check `docker version` and `docker compose version`. Use a Python
virtual environment for optional native backend development. Docker is sufficient
for migrations and database tests; no host PostgreSQL installation is required.

For an optional native Ubuntu backend environment on a fresh checkout:

```bash
sudo apt-get update
sudo apt-get install python3-venv python3-pip
python3 -m venv backend/.venv
backend/.venv/bin/python -m pip install -r backend/requirements.txt
cd backend
cp .env.example .env
.venv/bin/uvicorn app.main:app --reload
```

The native API defaults to memory and can run with the blank database password
in this example. Return to the repository root for Compose commands below.

On a fresh checkout, from the repository root:

```bash
cp .env.example .env
chmod 600 .env
python3 - <<'PY'
from pathlib import Path
import secrets
path = Path('.env')
content = path.read_text()
for key in ('POSTGRES_PASSWORD', 'POSTGRES_TEST_PASSWORD', 'POSTGRES_RUNTIME_PASSWORD'):
    content = content.replace(key + '=\n', key + '=' + secrets.token_hex(32) + '\n')
path.write_text(content)
PY
docker compose config --quiet
docker compose up -d --wait postgres
docker compose --profile tools run --rm --build migrate
docker compose --profile tools run --rm --build provision-runtime
# Edit root .env: set NEWS_STORAGE_BACKEND=postgres to opt in locally.
docker compose up -d --build backend frontend
```

Do not overwrite an existing `.env` or regenerate an established database's
password this way. The root `.env` controls Compose interpolation;
`backend/.env` is only for a native backend process. Examples contain no usable
password. `.env` and local backups are ignored by Git. Database access requires
owner `POSTGRES_PASSWORD` for schema tools and `POSTGRES_RUNTIME_PASSWORD` for
the Compose API. Importing/starting memory mode does not require DB access.

Compose uses `postgres` as the database hostname. PostgreSQL is not reachable
through `localhost:5432` by default. Prefer running database tools in the tools
container. Native Ubuntu development may continue to run the API/frontend
without DB access in memory mode. For native tools on Darkić's private network,
set `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_DB`, `POSTGRES_USER` and
`POSTGRES_PASSWORD` in `backend/.env` to that dedicated private instance. For
native API PostgreSQL mode, use restricted runtime credentials and set
`NEWS_STORAGE_BACKEND=postgres`. Native Alembic/provisioning commands need
separately supplied owner credentials; do not run the API with them. Root Compose
secrets do not automatically populate `backend/.env`.

SQLAlchemy builds an escaped URL from separate environment fields, including
passwords with `@`, `:`, `/` or `%`; its normal representation redacts passwords.
Sessions use bounded pools and connection timeouts, pre-ping, parameter hiding,
and rollback/close handling. `session_scope()` owns a commit/rollback unit of
work. The unused `get_db()` dependency does not implicitly commit on success;
future services must own their transaction boundaries.

`POSTGRES_SSLMODE` defaults to `prefer` for the private local container. A
self-hosted installation with PostgreSQL TLS configured can use `verify-full`
and supply the trusted CA through libpq's `PGSSLROOTCERT`. Never open the database
to the public internet or reuse another product's instance. Docker's
`POSTGRES_USER` is a bootstrap/schema-owner account used only by PostgreSQL,
migration tools and explicit provisioning. Compose maps `POSTGRES_RUNTIME_USER`
and `POSTGRES_RUNTIME_PASSWORD` to the backend's connection credentials.

## Runtime role provisioning

For an existing 15A checkout, preserve the initialized database and owner password.
Add the new storage/runtime entries from the root `.env.example` to the protected
root `.env`, generate a distinct runtime password, back up, and upgrade migrations
before provisioning. Do not replace the existing `.env` with the fresh template.

Run `docker compose --profile tools run --rm --build provision-runtime` after
upgrading migrations. It creates/rotates the dedicated login using bound password
parameters and quoted identifiers. Names are validated, passwords require at
least 24 characters, and existing privileged/owning/member roles are rejected
rather than repurposed. Provisioning is explicit and repeatable.

The role receives CONNECT, schema USAGE, function EXECUTE and
SELECT/INSERT/UPDATE/DELETE on the seven application tables. It receives no
table ownership, schema CREATE, TRUNCATE, migration-version access, role/database
creation, replication or superuser rights. The API rejects privileged or
owner-member connections. Re-run provisioning after migrations adding tables.

Rotate the protected root runtime password, re-run provisioning with owner
credentials, then recreate the backend to reload its runtime password and pools.
Never put owner credentials in runtime settings. Use `docker compose config
--quiet` for validation; unredacted Compose output includes secrets.

Passwords in an initialized PostgreSQL volume are not changed by editing `.env`.
Rotate them using an authenticated database operation and update clients together.
The named volume belongs to the Compose project: keep the project name stable.
`docker compose down` preserves it. `docker compose down --volumes` destroys it.
Container health checks test database availability, not migration readiness;
the API's `/` endpoint remains its existing liveness check.

## Migrations

```bash
docker compose --profile tools run --rm migrate alembic current
docker compose --profile tools run --rm migrate alembic upgrade head
docker compose --profile tools run --rm migrate alembic check
docker compose --profile tools run --rm migrate alembic history
```

The initial revision is `20261030_01`; Sprint 15B adds `20261030_02`, which
backfills literal and normalized aliases and replaces unbounded text uniqueness
with generated keys. Existing UUIDs and original source/article URLs are
preserved. Legacy articles with NULL external/canonical IDs are found again
through normalized aliases after migration. Source identity URLs are backfilled
using the same versioned rules.

Before alias writes, the migration preflights all source/article identities
under table write locks. Normalized source conflicts, cross-column article
conflicts, hash conflicts and malformed URLs abort with source/article UUIDs
and repair instructions. No rows are silently merged or reassigned. PostgreSQL
transactional DDL leaves the 15A schema/data intact after a failed upgrade;
resolve provenance explicitly and retry. Stop ingestion for this maintenance
operation and take a backup first. It scans the legacy dataset in memory and
requires an online Alembic connection; `upgrade --sql` cannot perform this
data-dependent preflight.

Revision `20261030_02` is still the unreleased migration in this branch. Do not
stamp/replay it over an already-populated local 15B database: recreate only a
disposable test database, or plan a separate reviewed data migration for that
dataset. No production database has been upgraded by this task.
Migrations do not call models' `create_all()` or seed live data. The normal
`alembic.ini` contains no credentials. The migration environment imports all
models and supports injected connections for isolated integration tests.

For future revisions, create them from a native development environment connected
to the dedicated development database, using `cd backend` and
`alembic revision --autogenerate -m description`. Review generated DDL before
applying it; autogenerated migrations do not substitute for data-migration design.
Rebuild the tools image after changing models or migrations. Do not use
`alembic downgrade base` to recover a populated application database: it drops
these tables. Downgrading to 15A also discards alias/metadata history and may fail
if long values cannot fit its original indexes; transactional DDL preserves 15B
on failure. Restore a verified backup rather than downgrading a live dataset.
Downgrade/re-upgrade verification below uses only the test instance.

new-app/new-engine recovery, stable stories, concurrency, long keys, restricted
privileges, interrupted runs, unavailable storage and a populated 15A upgrade.

malformed URL rollback and normalized legacy recollection/conflict diagnostics.

## Local collection and restart verification

After migrations/provisioning and explicit PostgreSQL opt-in:

```bash
curl -i http://localhost:8000/api/stories
curl -i 'http://localhost:8000/api/collect?limit_per_source=5'
curl -i 'http://localhost:8000/api/collect?limit_per_source=5'
docker compose restart backend
curl -i http://localhost:8000/api/stories
curl -i http://localhost:8000/api/editorial-queue
```

Before the first run expect `never_collected`. Unchanged repeated source data
should report zero new articles, the same story UUIDs and additional run history.
Existing connector failures remain visible in `source_results` and state
`partial`/`failed`. Verify counts and source attribution as an owner without
publishing PostgreSQL ports:

```bash
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT status, sources_processed, sources_failed, articles_total, articles_new FROM collection_runs ORDER BY started_at DESC;"'
```

Backend restart discards memory-mode stories and demo drafts; PostgreSQL article,
story and run data remain. For an isolated failure check, stop only the local
PostgreSQL service, request `/api/stories` and expect 503, then start PostgreSQL
and retry. Never perform outage checks against an active shared environment.

## Backup and recovery

Create a logical custom-format backup from the private container (root directory):

```bash
umask 077
mkdir -p backups
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' > "backups/hype-news-hub-$(date -u +%Y%m%dT%H%M%SZ).dump"
```

Check the command's exit code and archive contents, schedule backups on Darkić's
host, and retain encrypted copies on storage independent of the Docker volume.
The named volume is persistence, not a backup. Do not copy a running data directory
as an uncoordinated filesystem backup. `pg_dump` does not include cluster roles;
retain the separate role/credential provisioning procedure securely.

Restore first into a **new database**, using a PostgreSQL client of the same
major version, rather than overwriting the active one:

```bash
docker compose exec -T postgres sh -c 'createdb -U "$POSTGRES_USER" hype_news_hub_restore'
docker compose exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d hype_news_hub_restore --exit-on-error --no-owner --no-privileges' < backups/CHOSEN_BACKUP.dump
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d hype_news_hub_restore -v ON_ERROR_STOP=1 -c "SELECT version_num FROM alembic_version;"'
docker compose --profile tools run --rm -e POSTGRES_DB=hype_news_hub_restore migrate alembic current
docker compose --profile tools run --rm -e POSTGRES_DB=hype_news_hub_restore migrate alembic check
docker compose --profile tools run --rm -e POSTGRES_DB=hype_news_hub_restore provision-runtime
```

Verify expected counts, source attribution and application version compatibility
before an approved database cutover. Apply newer migrations to the restored
copy if required. Restore uses `--no-privileges`, so runtime grants must be
reapplied to the restored database before API verification/cutover. Keep the
original database/backup until recovery is verified.
Volume loss requires restoring a backup; restarting a container cannot recover
deleted data. Test restores regularly instead of relying only on successful dumps.

## Remaining work before production activation

1. Provision Darkić's dedicated Ubuntu host/database, protected owner/runtime
   secrets, private networking, durable storage, scheduled encrypted off-host
   backups and a verified restore. No production infrastructure was provisioned.
2. Run both migrations, provision/recheck runtime grants, and explicitly enable
   PostgreSQL mode. Keep Render on default memory until an approved cutover;
   memory history is not automatically imported and is lost on restart.
3. Configure HTTPS/reverse proxy and the browser-accessible API URL at frontend
   build time (existing Compose defaults target localhost). Keep database ports
   unpublished. Configure verified TLS if database traffic leaves the local host.
4. Add authentication/authorization before exposing editorial or collection
   operations. Complete live-source UAT and connector fixes for hypetv.rs/Hype
   Production in Sprint 15C; this sprint does not change connector routing.
5. Define monitoring, storage/statement time limits, retention and eventual
   pagination/candidate selection. Current reads/matching load retained stories;
   this is suitable for initial volumes, not an unbounded archive. The temporal
   gate bounds eligibility, not database reads. A subsequent performance sprint
   must add indexed candidate selection, targeted workspace reads, bounded API
   snapshots/pagination, payload projections and archive-growth load tests.
   Sprint 15B.1 deliberately does not introduce that pagination/API refactor.

Automatic background retries/scheduling, manual identity conflict resolution,
story merge/split tooling, article revision history and exact per-run article
membership are future work. Collection history currently stores per-source
counts/errors and first-seen article provenance, not a full historical payload
for every observation. Interrupted runs are repaired on the next collection,
not by a background worker. Editorial demo drafts remain in memory; persistent
approvals/version history, real Serbian AI generation and WordPress Draft
publishing remain separate work. Nothing in this sprint authorizes deployment.
